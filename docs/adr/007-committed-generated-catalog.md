# Commit The Generated Catalog

## Context

The catalog can be produced two ways. The server can parse the markdown corpus at startup, which for a few
hundred files with a YAML frontmatter reader is single-digit milliseconds and requires nothing beyond the files
themselves. Or the catalog can be generated by CI and committed as `catalog.json`.

The usual argument for committing an index is cost of construction, which applied while embeddings were under
consideration and disappeared once they were rejected
([ADR 006](./006-catalog-first-retrieval-no-embeddings.md)). The remaining arguments are different: a committed
catalog is inspectable and diffable in review, consumable by anything that can read one JSON file without
implementing markdown parsing, and gives the server a single trivial read path.

## Decision

`catalog.json` is generated from `snippets/` and committed. Markdown remains the sole source of truth; the
catalog is derived and must never be edited by hand. CI regenerates it and `validate.py` fails the build if the
committed file differs from what regeneration produces.

## Considered Options

Parsing at startup was recommended and not taken. It removes the generation step, the staleness check, and the
entire class of index-disagrees-with-markdown bugs, at the cost of the inspectability and simple-consumer
benefits above.

## Consequences

- A generated file lives in version control, so every corpus change produces a second diff, and contributors who
  forget to regenerate will fail CI. The failure message must say plainly how to fix it.
- Drift between catalog and corpus is possible in principle. The freshness check is the only thing preventing
  it, which makes that check load-bearing rather than incidental.
- Anyone can consume the corpus without a markdown parser, which lowers the barrier for tools other than the
  MCP server.
- Reversible at low cost: the server could switch to startup parsing and delete the artifact without touching a
  single corpus file.

## Status

Accepted — 2026-09-04.
